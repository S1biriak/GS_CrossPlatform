## 4. Границы предметной области

Приложение учитывает физические экземпляры книг, читателей и выдачи. Каждая запись Book — один физический экземпляр с уникальным InventoryNumber. Несколько одинаковых изданий имеют разные Id и инвентарные номера. ISBN, если указан, не является уникальным идентификатором экземпляра.

Это позволяет сохранить три предметных класса. Автор и жанр хранятся строками. Отдельные Author, Genre, BookCopy, Reservation, Payment в первую версию не входят. Штрафы, оплата, бронирование, уведомления и электронные книги также не входят в объём.

Учётные записи сотрудников/пользователей API отделены от читателей библиотеки. Reader описывает того, кому выдана книга; пользователь с ролью User или Admin описывает того, кто обращается к API. В первой версии клиент — приложение сотрудника библиотеки. Личный кабинет читателя и привязка учётной записи к читателю — возможное расширение с отдельной моделью прав.

## 5. Предметные классы

### Book — физический экземпляр книги

Данные: Id, InventoryNumber, Title, Author, Genre, PublicationYear, IsArchived.

Предлагаемые методы:

- UpdateDetails(...): проверка и изменение описания; обязательные строки не могут быть пустыми.
- EnsureCanBeLoaned(bool hasActiveLoan): запрет выдачи архивного или уже выданного экземпляра.
- Archive(bool hasActiveLoan): запрет архивирования экземпляра, пока он находится у читателя.
- Restore(): возврат экземпляра в действующий фонд.

Уникальность InventoryNumber проверяется сервисом и ограничением БД. Доступность вычисляется по незавершённым выдачам и IsArchived; отдельный изменяемый флаг IsAvailable не храним, чтобы не создавать два источника истины.

### Reader — читатель

Данные: Id, CardNumber, FullName, Email, IsBlocked. Лимит активных выдач — настраиваемое правило приложения, начальное значение 5.

Предлагаемые методы:

- UpdateContacts(...): проверка обязательного имени и корректности переданных контактов.
- Block() и Unblock(): изменение права на новые выдачи.
- EnsureCanBorrow(int activeLoanCount, int loanLimit): запрет новой выдачи заблокированному читателю или при достижении лимита.

CardNumber уникален. Блокировка не мешает возвращать уже выданные книги. Просрочка сама по себе не блокирует читателя автоматически: это отдельное возможное правило, которого нет в первой версии.

### Loan — выдача

Данные: Id, BookId, ReaderId, IssuedAtUtc, DueAtUtc, ReturnedAtUtc.

Предлагаемые методы:

- Create(...): создание выдачи с проверкой срока возврата.
- ChangeDueDate(...): изменение срока активной выдачи, который должен оставаться позже момента выдачи и текущего момента.
- Return(DateTimeOffset now): завершение активной выдачи; повторный возврат считается конфликтом состояния.
- IsOverdue(DateTimeOffset now): проверка просрочки.
- GetOverdueDays(DateTimeOffset now): количество начавшихся суток просрочки; после возврата расчёт фиксируется относительно ReturnedAtUtc.

Активная выдача определяется как ReturnedAtUtc == null. Просроченной активная выдача становится при now > DueAtUtc. Время получения книги и возврата задаёт сервер. Клиент передаёт желаемый срок возврата при выдаче; если он отсутствует, применяется срок 14 дней.

Идентификаторы книги и читателя существующей выдачи не изменяются через PUT. PUT меняет разрешённые редактируемые поля, прежде всего DueAtUtc. Это явно описывается в DTO и OpenAPI. Возврат оформляется отдельной предметной операцией.

## 6. Правила целостности и ошибки

1. Нельзя выдать отсутствующую или архивную книгу.
2. У одного экземпляра не может быть двух активных выдач.
3. Нельзя создать выдачу отсутствующему или заблокированному читателю.
4. Нельзя превысить лимит активных выдач читателя.
5. Срок возврата должен быть позже момента выдачи.
6. Нельзя повторно вернуть уже возвращённую книгу.
7. Архивирование книги с активной выдачей запрещено.
8. Нельзя удалить книгу или читателя, на которых ссылается история выдач: 409 Conflict. Для книги предусмотрен архив, для читателя — блокировка.
9. Активную выдачу удалить нельзя: сначала необходимо вернуть книгу. Удаление завершённой выдачи доступно администратору как учебная CRUD-операция исправления данных; оно удаляет соответствующую часть истории и влияет на отчёты.
10. InventoryNumber и CardNumber уникальны; конфликт возвращает 409.
11. Неверный формат или пустые обязательные поля: 400. Отсутствующий ресурс: 404. Конфликт с состоянием: 409.

Проверка доступности и сохранение выдачи выполняются согласованно. В БД предусматривается уникальный частичный индекс по BookId для строк с ReturnedAtUtc IS NULL. Проверка лимита читателя и создание выдачи выполняются в транзакции с учётом поведения SQLite; конфликты записи обрабатываются. Проверка только в C# без защиты от одновременных запросов недостаточна.

Для создания и редактирования используются отдельные DTO: клиент не может назначить себе роль, установить внутренние флаги или самостоятельно заполнить время возврата. Ошибки имеют согласованный формат ProblemDetails; для 401/403 сохраняются корректные HTTP-коды и заголовки механизма аутентификации.

Фильтры книг: search по названию/автору/инвентарному номеру, genre, availableOnly, includeArchived. Фильтры выдач: readerId, bookId, activeOnly. Начальная сортировка книг — по названию и Id. Пустая выборка возвращает 200 и пустой items.

## 8. Четыре отчёта и LINQ

### Активные выдачи

Loan + Book + Reader. Поля результата: loanId, inventoryNumber, bookTitle, readerId, readerName, issuedAtUtc, dueAtUtc, isOverdue.

LINQ: Where для активных выдач, Join для связей, Select для DTO, OrderBy для срока возврата.

### Просроченные активные выдачи

Loan + Book + Reader. Поля: данные книги и читателя, срок, количество суток просрочки. Время now фиксируется один раз на весь запрос. ReturnedAtUtc заполнено — запись в этот отчёт не входит.

LINQ: Where по состоянию и сроку, Join, Select, OrderByDescending по просрочке. Расчёт, который провайдер SQLite не переводит в SQL, выполняется после ограниченной выборки в памяти; в документации отмечается граница IQueryable/IEnumerable.

### Популярность экземпляров

Book + Loan. Количество выдач экземпляра за период по IssuedAtUtc, название, автор и инвентарный номер. Это рейтинг физических экземпляров, а не объединённый рейтинг произведений. Экземпляры с нулём выдач не входят.

LINQ: Where по периоду, Join, GroupBy, Count, Select, OrderByDescending и ограничение размера результата.

### Статистика читателей

Reader + Loan. Общее число выдач за период, число возвращённых, активных и просроченных среди выдач выбранного периода. Читатели без выдач также включаются с нулевыми значениями.

LINQ: GroupJoin/DefaultIfEmpty либо эквивалентная проекция связанных коллекций, Select, Count с предикатом. Фильтр периода применяется к выдачам до объединения, чтобы не исключить читателей с нулевой статистикой.

Общие правила периода: from включительно, to исключительно. Даты описываются как UTC-моменты. Для текущих активных/просроченных выдач отчёт отражает состояние на момент запроса; исторические снимки состояния не восстанавливаются. Для объёмных отчётов предусматриваются пагинация или ограничение результата, описанные в OpenAPI.

## 9. Аутентификация и авторизация

- Две роли: User и Admin. Все изменения данных доступны Admin.
- Публично доступен каталог книг и метод входа. Читатели, выдачи и все отчёты требуют входа. Это уточняет предварительную схему, чтобы данные читателей не были публичными.
- Две демонстрационные учётные записи; открытой регистрации и выбора роли клиентом нет.
- Пароли хранятся в виде хешей через стандартный PasswordHasher; хеши не возвращаются через API.
- Ключ подписи JWT задаётся через user-secrets/переменную окружения; реальный ключ не коммитится и не включается в Postman.
- Демонстрационные пароли и настройка первого запуска отдельно описываются в инструкции; одинаковый комплект настроек должен работать и с Release-сборкой.
- Токен содержит идентификатор, имя и роль, имеет ограниченный срок действия. Проверяются подпись, issuer, audience и срок действия.
- Вход возвращает accessToken, expiresAtUtc и сведения о пользователе. Пароль и ключ подписи никогда не попадают в ответ.
- 401: нет подходящего действительного токена. 403: токен действителен, роль не даёт права выполнить операцию.
- Для этой локальной учебной работы предусматривается собственный метод выдачи JWT. Полноценный внешний провайдер OAuth/OIDC не входит в объём.

## 10. Подготовка к клиентской лабораторной

- Контроллеры принимают и возвращают DTO; внутренние EF-сущности и passwordHash не являются контрактом клиента.
- Стабильные маршруты /api/v1, предсказуемые ответы, согласованные ошибки и OpenAPI.
- Время и часовой пояс явно описаны, формат не зависит от языка Windows.
- JWT передаётся через Authorization: Bearer; адрес API настраивается в клиенте.
- CORS настраивается списком разрешённых адресов для браузерного клиента; конкретный origin добавляется после выбора клиента. Для настольного клиента CORS не нужен.
- Книги, читатели и выдачи имеют фильтры и пагинацию, пригодные для таблиц и форм выбора.
- Отдельные операции return, block, archive позволяют сделать понятные кнопки в клиенте.
- Запросы чтения не меняют состояние приложения.
- Будущий UI ориентирован на сотрудника: User просматривает данные и отчёты; Admin управляет фондом, читателями и выдачами.
- Выбор WPF/MAUI/Avalonia/веб-клиента откладывается до получения ТЗ следующей работы; API не привязывается к конкретному UI.

## 12. Порядок выполнения и критерии завершения

### Этап 1. Зафиксировать проектирование

Результат: этот план с моделью, правилами, маршрутами, ролями и соответствием баллам. На этапе реализации допустимы уточнения имён/DTO без расширения предметной области.

### Этап 2. Создать основу

Создать решение и проекты, конфигурацию, Swagger/OpenAPI, обработку ошибок, .gitignore и фиксацию совместимого SDK. Инициализировать локальный Git. Не включать секреты, локальные БД, bin/obj и персональные настройки IDE в коммиты.

Готово, когда решение открывается в VS 2022, собирается и запускает пустое API.

### Этап 3. Реализовать модель и хранение

Добавить Book, Reader, Loan, методы, DTO, DbContext, миграции и ограничения БД. Подготовить воспроизводимые синтетические данные: несколько экземпляров одного названия, доступные и архивные книги, активные/возвращённые/просроченные выдачи, заблокированный читатель, читатель у лимита и читатель без выдач.

Первый запуск создаёт БД и добавляет начальные данные однократно. Сброс демонстрационной БД допускается только явной локальной командой, не публичным endpoint. Временные значения демонстрационных выдач задаются так, чтобы на первом показе действительно были просрочки.

Готово, когда данные сохраняются после перезапуска, а ограничения работают при ошибочном и конкурентном вводе.

### Этап 4. Реализовать CRUD и предметные операции

Создать три контроллера, сервис выдачи/возврата, поиск, пагинацию, архивирование и блокировку. Настроить ответы 200/201/204/400/404/409 и заголовок Location.

Готово, когда можно добавить книгу и читателя, выдать и вернуть книгу, изменить данные и удалить разрешённые записи; неверные действия дают объяснимые ошибки без повреждения БД.

### Этап 5. Реализовать четыре отчёта

Добавить LINQ-запросы и DTO результатов. На небольшом фиксированном наборе вручную сверить состав отчётов и количества. Проверить пустые выборки, границы периода, читателя без выдач и сортировку при равных значениях.

Готово, когда каждый отчёт объединяет разные классы и возвращает проверенный результат.

### Этап 6. Добавить авторизацию

Добавить учётные записи, хеширование паролей, login/me, JWT и атрибуты/политики доступа. Отделить конфигурацию запуска от секретов. Проверить вход администратора и пользователя, неправильный пароль, отсутствие и истечение токена, 401 и 403.

Готово, когда обычный пользователь читает отчёты, но не изменяет данные, а администратор выполняет все разрешённые операции.

### Этап 7. Проверить поведение

Модульные тесты: сроки выдачи, возврат, просрочка, блокировка, лимит, архивирование. Интеграционные тесты: CRUD, FK/уникальные ограничения, повторная выдача, транзакции/одновременные попытки выдачи и матрица доступа. Для реляционных проверок использовать SQLite, а не EF InMemory. Управляемое время позволяет избежать нестабильных тестов просрочки.

Готово, когда значимые правила проверены, сборка Release проходит, результаты отчётов подтверждены.

### Этап 8. Подготовить Postman

Папки коллекции: Auth, Books, Readers, Loans, Reports, Authorization, Validation. Переменные: baseUrl, userToken, adminToken, bookId, readerId, loanId. Вход автоматически сохраняет токен; создание — ID. Окружение не содержит ключ подписи JWT.

Сценарии: полный CRUD всех сущностей, выдача/возврат, четыре отчёта, гость 401, User 403, Admin успешное создание, неверный пароль, 400, 404, 409, повторная выдача, повторный возврат, лимит читателя. Проверки статусов и значимых полей выполняются скриптами Postman.

Коллекция создаёт собственные тестовые данные с уникальными номерами и очищает их в правильном порядке. Повторный запуск не требует ручной замены ID и не разрушает начальный демонстрационный набор.

Готово, когда коллекция проходит целиком на опубликованной сборке.

README: требования, запуск из VS/CLI и архива, настройка секретов и демонстрационных аккаунтов, импорт Postman, описание БД и соответствие пунктам ТЗ.

DEMO_SCENARIO: последовательность запросов для показа на паре и ожидаемые результаты.

Готово, когда по инструкциям можно повторить запуск и объяснить, как запрос доходит от контроллера до БД и возвращает ответ.

### Этап 10. Выпустить Release

Собрать self-contained публикацию win-x64 в конфигурации Release, включить необходимые зависимости и проверить запуск из отдельного каталога с чистой БД. Предусмотреть запуск без профиля Visual Studio, заданный локальный адрес/порт и доступность документации в демонстрационном режиме. Демо-скрипт должен явно передавать настройки, необходимые опубликованному приложению; user-secrets не считаются автоматически доступными Release.

Создать GitHub-репозиторий, отправить исходники, создать тег v1.0.0 и GitHub Release. Приложить архив приложения, Postman collection/environment и инструкцию. Архив исходников GitHub не заменяет готовую сборку. Проверить комплект по скачанному архиву. Подготовить ссылку на страницу релиза для самостоятельной отправки преподавателю.

Готово, когда релиз опубликован, его файлы воспроизводимо запускаются и все обязательные сценарии демонстрируются на компьютере студента.

## 14. Опорные пояснения для защиты

- API — HTTP-интерфейс для клиента; отсутствие собственной веб-страницы не мешает приложению быть Web API.
- CRUD описывает операции с ресурсами. Выдача и возврат дополнительно отражают предметные действия и проверяют бизнес-правила.
- Модель содержит правила, которые должны сохраняться независимо от будущего интерфейса. Проверка только в форме клиента легко обходится прямым HTTP-запросом.
- DTO ограничивает входные поля и отделяет публичный контракт от структуры таблиц.
- LINQ Where отбирает записи, Select преобразует их форму, Join связывает сущности, GroupBy формирует группы для агрегации. GroupJoin позволяет сохранить строки без связанных данных.
- EF Core переводит поддерживаемые LINQ-выражения IQueryable в SQL; после материализации дальнейший LINQ выполняется в памяти.
- Аутентификация устанавливает личность, авторизация проверяет права. Действительный токен не означает наличие роли администратора.
- JWT подписан; обычный подписанный JWT не является шифрованием содержимого. Секретные данные в payload не помещаются.
- Проверка доступности в приложении даёт понятную ошибку, а ограничение БД дополнительно защищает от параллельных запросов.
- Кроссплатформенность относится к платформе и исходному приложению; self-contained архив win-x64 предназначен для Windows. Для Linux/macOS нужна соответствующая публикация и отдельная проверка.
- Release-конфигурация — способ сборки, GitHub Release — опубликованная версия с тегом и материалами.
