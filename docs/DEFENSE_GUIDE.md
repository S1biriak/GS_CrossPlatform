# Подробные пояснения для защиты Library API

## 1. Что делает приложение

Library API хранит экземпляры книг, читателей и выдачи. Клиент обращается к серверу по HTTP, отправляет JSON и получает JSON с данными либо ProblemDetails с описанием ошибки. Контроллеры не возвращают HTML-страницы. Swagger — вспомогательный интерфейс изучения и проверки HTTP-контракта.

Предметная модель содержит ровно три класса: Book, Reader, Loan. Остальные классы обслуживают HTTP, БД, настройки, аутентификацию и тестирование. Учётная запись AppUser отделена от Reader: сотрудник использует приложение, читатель получает книгу. Это важно для следующей лабораторной: интерфейс сотрудника может управлять многими читателями.

## 3. Почему это модель с бизнес-логикой

Класс, содержащий только свойства, описывает форму данных. В задании требуются также правила работы с ними. Например, ReturnedAtUtc нельзя произвольно менять: возврат разрешён только один раз и не может предшествовать выдаче. Метод Loan.Return проверяет это до изменения состояния.

Свойства предметных классов имеют private set. Внешний код вызывает методы, а не обходит правила прямым присваиванием. EF Core умеет загружать такие свойства через отображение модели. Приватный конструктор без параметров нужен EF, публичный конструктор/фабрика — корректному созданию новых объектов.

Book.EnsureCanBeLoaned запрещает выдачу архива или уже занятого экземпляра. Archive не позволяет спрятать книгу, которая находится у читателя. Restore снова делает экземпляр действующим, но его фактическая доступность всё равно зависит от активной выдачи.

Reader.EnsureCanBorrow проверяет блокировку и лимит. Количество активных выдач передаёт сервис, потому что отдельный объект Reader не должен самостоятельно подключаться к БД. Block и Unblock выражают предметное действие. Блокировка запрещает новые выдачи, но не возврат старых.

Loan.Create проверяет идентификаторы и даты; ChangeDueDate работает только для активной выдачи; Return завершает её; IsOverdue и GetOverdueDays вычисляют просрочку. Статус не хранится отдельной строкой, поскольку определяется датами: ReturnedAtUtc != null означает завершение, отсутствие даты — активность.

## 4. Физический экземпляр и связи

Book — конкретная физическая книга. У двух экземпляров «Мастера и Маргариты» разные инвентарные номера, и выдавать их можно независимо. Использовать название или ISBN как уникальный идентификатор физической книги было бы неверно.

Loan.BookId — внешний ключ к Book.Id; Loan.ReaderId — внешний ключ к Reader.Id. Одна книга и один читатель могут участвовать во многих выдачах в разное время. Каждая выдача ссылается ровно на один экземпляр и одного читателя.

Отдельные сущности автора, жанра и экземпляра не введены ради ограничения трёх классов. Название произведения и физический экземпляр можно разделить в большем проекте, но для этой лабораторной достаточно выбранной модели.

## 5. Как проходит HTTP-запрос

Пример: POST /api/v1/loans.

1. Сервер принимает HTTP-запрос; middleware аутентификации проверяет Bearer-токен.
2. Авторизация проверяет роль Admin. При отсутствии подходящего токена запрос завершится 401, при недостаточной роли — 403.
3. MVC выбирает LoansController.Create по маршруту и HTTP-методу.
4. JSON превращается в CreateLoanRequest. Атрибуты [Range], [Required] и [ApiController] обеспечивают автоматическую проверку формата. Неизвестные поля отклоняются.
5. Контроллер вызывает LoanService.Create и передаёт CancellationToken запроса.
6. Сервис открывает транзакцию, получает книгу и читателя, проверяет доступность и лимит.
7. Методы модели проверяют предметные правила. Loan.Create устанавливает время выдачи, которое предоставляет сервер.
8. EF Core создаёт INSERT; SQLite проверяет внешние ключи и уникальные индексы.
9. После SaveChangesAsync транзакция фиксируется.
10. Сервис получает LoanDto, контроллер отвечает 201 Created с Location, указывающим адрес новой выдачи.

Если правило нарушено, DomainException преобразуется в ProblemDetails. При неожиданной ошибке клиент получает общий текст и traceId, подробности остаются в серверном журнале.

## 6. Почему нужны DTO

DTO — форма данных на границе HTTP. CreateBookRequest позволяет задать описание и инвентарный номер. BookDto дополнительно возвращает Id, IsArchived и вычисленный IsAvailable. Эти поля нельзя произвольно назначить входным JSON.

Разделение предотвращает нежелательное массовое присваивание полей, исключает выдачу passwordHash и позволяет менять внутреннюю структуру БД без немедленного изменения клиентских форм. При попытке передать isBlocked в UpdateReaderRequest сервер вернёт 400; для блокировки существует отдельная операция.

У PUT выдачи разрешённое изменяемое поле — DueAtUtc. BookId и ReaderId уже оформленной выдачи не редактируются. Возврат — отдельный POST на /return, потому что у него собственные проверки и серверное время.

## 7. LINQ: что означает каждый оператор

Where оставляет элементы, удовлетворяющие условию. Например, ReturnedAtUtc == null отбирает активные выдачи. Select строит из найденных данных объект нужной формы — DTO. Это выполняет обязательный минимум задания.

Join связывает две последовательности по равным ключам. В активных выдачах сначала сопоставляются Loan.BookId и Book.Id, затем Loan.ReaderId и Reader.Id. В одном результате появляются название, читатель и срок возврата.

GroupBy объединяет строки в группы. В рейтинге книга группируется по идентификатору и описанию, затем Count считает выдачи. OrderByDescending располагает наиболее популярные экземпляры первыми; ThenBy по Id делает порядок однозначным при равенстве.

Статистика читателей использует коррелированные Count по связанным выдачам. Читатель остаётся в результате даже при нуле выдач. Обычный внутренний Join исключил бы таких читателей. EF переводит этот вариант в SQL с подзапросами; по результату он выполняет нужную задачу объединения двух классов.

IQueryable хранит выражение запроса. Пока не вызваны ToListAsync, CountAsync или SingleOrDefaultAsync, запрос обычно не выполняется. EF переводит поддерживаемые выражения в SQL. После материализации мы получаем обычные объекты и LINQ работает в памяти.

В отчёте просрочек SQL сначала отбирает, сортирует и ограничивает строки нужной страницей. Только вычисление Ceiling для числа суток выполняется в .NET после материализации этой страницы. Это не загружает всю таблицу в память.

Рейтинг строит анонимную проекцию групп, сортирует её и затем создаёт DTO. Такой порядок проверен на SQLite; произвольная перестановка проекций может сделать выражение непереводимым в SQL.

## 8. Четыре отчёта

Активные выдачи объединяют три класса и показывают текущее состояние. Просроченные выдачи дополнительно требуют DueAtUtc < now и пустой ReturnedAtUtc. Точно в момент срока просрочки ещё нет; на одну секунду позже — уже есть, а число начавшихся суток равно одному.

Популярность относится к физическим экземплярам. Если два экземпляра одного названия выдавались по разу, это две строки рейтинга с LoanCount = 1. Начальный экземпляр LIB-001 имеет две выдачи: завершённую и текущую.

Статистика читателя считает выдачи, оформленные в выбранный период. TotalLoans = ReturnedLoans + ActiveLoans; OverdueLoans является подмножеством ActiveLoans. Период не восстанавливает историческое состояние: если книга возвращена сейчас, она считается возвращённой и при фильтрации по более ранней дате её выдачи.

Границы периода: from включительно, to исключительно. Соседние периоды не посчитают пограничную выдачу дважды. Читатель без выдач сохраняется даже при пустом периоде.

## 9. EF Core, SQLite и миграции

DbContext — объект работы с БД на один HTTP-запрос. Он предоставляет DbSet, строит запросы и отслеживает изменения загруженных сущностей. После вызова методов модели SaveChangesAsync сохраняет изменённые свойства.

AsNoTracking отключает отслеживание для запросов чтения, где оно не нужно. Проекции дополнительно выбирают только нужные данные.

Миграция InitialLibrary создаёт таблицы, внешние ключи, проверки дат и индексы. Файлы миграции и ModelSnapshot включаются в Git. На запуске Database.MigrateAsync применяет ещё не выполненные миграции. LibraryDesignTimeFactory позволяет генерировать схему, не поднимая HTTP и не требуя JWT-ключа.

SQLite выбрана из-за простого запуска: файл БД и библиотека провайдера без отдельного серверного процесса. Приложение сохраняет данные между запусками. Это полезно и для будущего клиента.

SQLite не сохраняет DateTime.Kind. ValueConverter восстанавливает Utc при чтении. Публичные входные даты DateTimeOffset переводятся в UtcDateTime; внутренние даты сравниваются в одной системе времени.

Встроенный lower SQLite не обеспечивает нужный поиск для всех русских букв. SqliteFunctionsInterceptor регистрирует dotnet_contains на каждом соединении, а LibraryDbFunctions отображает этот метод в SQL. Функция использует StringComparison.OrdinalIgnoreCase. Проверка поиска «МАСТЕР» по «Мастер» присутствует в интеграционном тесте.

## 10. Одновременные запросы и история

Два запроса могут почти одновременно проверить, что книга свободна. Если ограничиться проверкой в C#, оба способны попытаться создать выдачу. Поэтому в БД есть уникальный индекс BookId с фильтром ReturnedAtUtc IS NULL: для одного экземпляра допускается только одна активная выдача, но много завершённых.

Выдача начинается с немедленной транзакции SQLite. Параллельные записи сериализуются; проверка лимита читателя и вставка находятся в одной транзакции. Иначе два запроса к разным книгам могли бы одновременно увидеть свободное последнее место лимита.

Индекс не заменяет проверку модели: проверка даёт понятную предметную ошибку, индекс защищает целостность при конкуренции и обходе сервиса. Обе ситуации проверяются тестами: два конкурентных HTTP-запроса и прямая вставка через DbContext.

Связанные Book и Reader удаляются с Restrict. Для сохранения истории предусмотрены архивирование и блокировка. Завершённую Loan можно удалить администратору ради полного учебного CRUD; это намеренное исправление данных, которое изменит статистику. В реальной библиотеке обычно потребовались бы аудит и более строгая политика удаления.

## 11. JWT, пароли и роли

Аутентификация отвечает на вопрос, кто обращается к API. Авторизация определяет разрешённые операции. JWT Bearer используется для передачи подтверждения входа между HTTP-запросами.

AuthService ищет логин, проверяет пароль через PasswordHasher, затем создаёт JWT с sub, unique_name, role и jti. Пароли хранятся как солёные адаптивные хеши. Хеширование не является обратимым шифрованием. Для отсутствующего логина также выполняется проверка фиктивного хеша, чтобы сократить различие времени ответа.

JWT состоит из заголовка, полезной нагрузки и подписи. Обычный подписанный JWT не скрывает содержимое: Base64Url можно декодировать. Подпись позволяет серверу обнаружить изменение содержимого. Клиент не должен помещать в токен пароли и не может самостоятельно назначить себе Admin без нарушения подписи.

Сервер проверяет алгоритм HMAC SHA-256, подпись, issuer, audience и срок. MapInboundClaims отключён, имена claims явно согласованы. ClockSkew = 0 исключает дополнительное окно после срока действия.

Ключ создаётся криптографическим генератором и хранится в игнорируемой локальной конфигурации. Он не попадает в исходники, Postman, БД или архив релиза. Релиз генерирует собственный ключ при первом запуске. Пароли демонстрационных аккаунтов публичны специально для локальной учебной проверки; это не личные пароли пользователя.

[Authorize] требует входа, [Authorize(Roles = Roles.Admin)] дополнительно требует роль. Без токена или с испорченным/просроченным токеном — 401 и Bearer challenge. С User-токеном на административной операции — 403. Роль Admin имеет право и читать отчёты, и изменять данные.

Токены действуют 30 минут. Refresh-токены, внешняя OAuth/OIDC-служба и регистрация не реализованы, поскольку не нужны для этого задания. В учебном замкнутом приложении собственный метод login демонстрирует механизм. Личный кабинет читателя потребовал бы связи AppUser с Reader и ограничения доступа по владельцу.

## 12. HTTP и ошибки

GET читает без побочных эффектов. POST создаёт ресурс или выполняет явно названную предметную операцию. PUT меняет разрешённую форму существующего ресурса. DELETE удаляет разрешённую запись.

201 с Location позволяет клиенту узнать URI созданного объекта. 204 означает успешное удаление без тела. 400 — входные данные не соответствуют контракту; 404 — ресурс отсутствует; 409 — запрос понятен, но конфликтует с текущим состоянием, например книга уже выдана.

ProblemDetails унифицирует ошибки: status, title, detail/validation errors, instance и traceId. Клиенту не нужно разбирать SQL-исключение или HTML. ApiExceptionHandler сопоставляет предметные и ожидаемые SQLite-конфликты с HTTP, а непредвиденные ошибки журналирует.

CancellationToken передаётся в запросы EF: если клиент отменил запрос, сервер может отменить незавершённую операцию. async/await позволяет не удерживать поток в ожидании ввода-вывода. Это не означает автоматическое параллельное выполнение нескольких операций одного DbContext.

## 13. Подготовка будущего клиента

Клиенту доступны стабильные /api/v1, DTO и OpenAPI. Поля JSON используют camelCase. Списки включают items и totalCount, чтобы клиент мог построить таблицу и переключатель страниц. Сортировка детерминирована, pageSize ограничен.

Для браузерного клиента CORS ограничивается известными origin в настройках. CORS — правило браузера о доступе к ответу другого origin, оно не заменяет JWT и не запрещает прямой запрос через Postman. Для настольного клиента браузерного ограничения нет.

Все предметные проверки выполняются на сервере. Будущая форма может заранее подсветить ошибку, но не становится единственным местом проверки лимита, роли или доступности.

## 14. Как доказать корректность

Модульные тесты создают объекты без HTTP и БД: проверяют границу просрочки, окончательность возврата, лимит, архивирование и недопустимые значения. Интеграционные тесты поднимают настоящее ASP.NET Core приложение в TestServer и используют настоящую SQLite-БД во временном файле.

SQLite в тестах важна: EF InMemory не воспроизвела бы SQL-перевод LINQ, FK и частичный уникальный индекс. Время зафиксировано TimeProvider на момент начала тестового процесса; даты демонстрационного набора относительно него постоянны. JWT проверяется реальным обработчиком.

Postman проверяет уже запущенный HTTP-сервер, получает токены и выполняет запросы. Коллекция пригодна для ручной защиты и автоматического Newman. Запуск опубликованной сборки дополнительно проверяет упаковку зависимостей и настройки вне Visual Studio.

## 15. Вопросы преподавателя и краткие ответы

**Где бизнес-логика?** Book.Archive/EnsureCanBeLoaned, Reader.EnsureCanBorrow, Loan.Create/ChangeDueDate/Return/GetOverdueDays. Сервис вызывает эти методы, а не просто копирует свойства DTO.

**Где Where и Select?** В ReportService.Active и Overdue, а также в поиске CatalogService. Для объединения используются Join, для рейтинга — GroupBy и Count.

**Почему User не может добавить книгу?** Метод контроллера требует роль Admin; действительный User-токен приводит к 403.

**Почему без токена 401?** Невозможно установить действительную аутентификацию для защищённого маршрута; роль ещё не проверяется.

**Почему книга и читатель не удаляются с историей?** Restrict защищает ссылки выдач, а сервис возвращает объяснимый 409. Используются архив и блокировка.

**Что будет при одновременной выдаче?** Транзакция и частичный уникальный индекс обеспечивают одну активную выдачу; второй запрос получит конфликт. Это проверено отдельным тестом.

**Что означает Release?** Оптимизированная конфигурация публикации приложения. GitHub Release — отдельная опубликованная версия с тегом, бинарным архивом и инструкцией.

**Почему проект кроссплатформенный, если архив Windows?** ASP.NET Core и исходники допускают публикацию под другие поддерживаемые ОС. Конкретный архив win-x64 предназначен только для Windows; запуск на Linux/macOS требует другой публикации и проверки.

**Почему нет отдельной таблицы авторов?** В задании требуется небольшая модель из трёх классов; выбранные строки достаточны для учебной предметной области и четырёх отчётов.
